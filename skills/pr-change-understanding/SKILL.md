# 弄懂代码改动

当不确定一个改动或 PR 的行为是否正确，或担心自己没真正理解 AI 辅助完成的改动时使用。目标不是让 AI 说对，而是让用户自己能回答维护者的追问。

## 原则

- 环境和批量对照可以交给 agent。最关键的 1 到 2 个现象必须用户亲手跑。
- 每次运行前先写下预期。猜错的地方就是没理解的地方。
- 区分三类信息：亲自验证的事实、代码确认的调用链、推测。推测不得写成事实。
- 判断"懂了"的标准：不看稿子，能用两三句话讲清动机，并能自己回答追问。

## 步骤

1. **最小复现**
   找一条能暴露问题的最小请求，而不是一上来跑完整测试矩阵。服务就绪后再发请求，避免把启动失败当成行为差异。只保留能改变结论的变量。

2. **先猜后跑**
   运行前写下预期结果，包括正常路径和边界值。跑完只对照差异：哪里猜对，哪里猜错，错在哪个假设。用差异决定下一刀实验，不要连续盲跑。

3. **对上改动**
   把每个现象对应到具体 commit、PR 或代码路径。一个现象一个归属。对不上的现象标成未解释，不并进已确认的结论。

4. **自己讲出为什么**
   合上稿子，用两三句话讲清：谁需要这个行为，输入输出是什么，为什么这样改。讲不出来时，把问题拆小，只给提示和纠错，不直接给答案。能讲清后再进入输出。

## 输出

理解建立之后，用六段式口述或速记：

1. 背景与调用链
2. 问题和指标
3. 根因
4. 方案与取舍
5. 结果
6. 复盘

四步法是输入端，负责亲手把理解建起来。六段式是输出端，负责把已建立的理解讲给别人听。每一段都标明依据来自亲手验证、代码确认，还是推测。
