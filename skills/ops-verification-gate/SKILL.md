# Ops Verification Gate

用于高风险运维事件，在证据不足、生产故障、恢复演练或待批准变更中，以统一事件包控制从诊断到授权、执行、验收和停止的状态转换。

## 运行契约

事件期间只维护两个运行文件：本 `SKILL.md` 与 `ops-packet.yaml`。`ops-packet.yaml` 是单一事实状态包。不要另建平行计划、批准记录或验收摘要。

默认只读、最小权限、最小凭据。不得提取与当前验证无关的密钥，不得依赖疑似故障域内的唯一观测路径。

`risk_level` 只描述风险，不代表授权。CI 通过、PR 合并、文档完成、诊断正确、用户表示关注或含糊确认，都不构成生产执行授权。

## 状态机

仅按以下顺序推进：

`context_pending -> investigating -> diagnosis_supported -> awaiting_authorization -> authorized -> applying -> observing -> verifying -> accepted`

任何阶段都可进入：

`stopped`：证据不足、授权缺失、条件不满足或继续操作不安全。

`rolling_back -> rolled_back -> stopped`：变更失败、触发回滚条件或出现非预期影响。

不得跳过 `diagnosis_supported` 或 `authorized` 进入变更。若根因未被适当证据支持，或批准不明确，只能继续只读调查或停止。

## 1. 建立 Context Manifest

先填写 `ops-packet.yaml` 的 `metadata`、`context` 与 `criteria`：

1. 标识事件、环境、目标、影响面、故障域、时间边界和当前状态。
2. 列出 authoritative sources，例如仓库约束、runbook、实时控制面、监控、审计日志和目标环境状态。
3. 声明搜索根、已命中材料、尚未读取的范围和不可用来源。
4. 区分声明状态、仓库状态、控制面状态、数据面状态和用户可见行为。不要用一个层面的成功替代另一个层面。
5. 写明权限、允许的只读操作、禁止动作以及可用的替代观测路径。
6. 分别记录 `risk_level` 和 `authorization`。无明确授权时，授权状态必须是 `not_granted`。

若 Context Manifest 不完整、来源冲突或目标不明确，不得执行变更。

## 2. 每轮只验证一个可证伪假设

每轮调查必须：

1. 写一个 `active_hypothesis`，包含预测结果和可推翻它的结果。
2. 选择一条下一命令或一个原子观察动作，不并行扩张范围。
3. 说明该动作读取什么、为何安全、预计产生哪类证据。
4. 执行后记录结果、时间、来源和可靠性。
5. 将假设标记为 `supported`、`rejected` 或 `inconclusive`，再决定下一轮。

优先从实际执行上下文观测。例如验证工作负载问题时，应在工作负载实际使用的 DNS、代理、身份和网络上下文中取证，而不是只采信外部主机视角。

若主要访问路径属于疑似故障域，优先使用既有授权的独立路径、静态回程、公开端点或控制面对比。不要为诊断便利临时扩大访问面。

## 3. 按证据等级约束结论

为每项证据标注一个等级：

- `E1 Artifact`：配置、清单、代码、文档、声明式期望或静态产物。
- `E2 State`：目标环境的实时状态、对象、进程、日志、指标或控制面快照。
- `E3 Path`：逐跳路径证据，例如 DNS、TCP、TLS、HTTP、代理、Ingress、工作负载、存储链路。
- `E4 Behavior`：在目标环境和目标身份下执行真实操作所得的行为结果。
- `E5 Recovery`：真实回滚、恢复、重建、读取比对或故障后恢复证据。

等级表示证据覆盖范围，不表示可以自动外推。每项验证必须同时填写：

- `claim_supported`：该证据直接支持什么。
- `does_not_prove`：该证据仍不能证明什么。

示例规则：连通性不能证明认证语义；认证 canary 不能证明服务级可恢复性；仓库 CI 不能证明生产能力或生产授权；外部端点成功不能证明特定客户端或工作负载路径；备份成功不能证明恢复成功；Agent 自报不能证明真实最终状态。

结论所需证据必须与 claim 的层级、身份、环境和时间窗口匹配。需要恢复保证时，必须取得 `E5 Recovery`，不能停在传输或备份成功。

## 4. 形成诊断并请求明确授权

只有当证据能排除关键替代解释，并将失败定位到足以设计单一最小修复的层级时，才可将状态设为 `diagnosis_supported`。

授权请求必须绑定：

- `packet_revision`
- 精确目标与作用域
- 已确认根因和证据引用
- 冻结后的单一最小 diff
- 预期影响与 `risk_level`
- success、rollback、stop conditions
- 有界观察窗口
- 回滚步骤与回滚可行性证据

批准必须记录准确用户原话或外部批准包引用、批准人、时间、作用域和绑定 revision。不得把“继续看看”“可以处理”“按需修复”等含糊表达解释为批准。

以下关键输入变化时必须递增 `packet_revision`，并将旧批准设为 `invalidated`：目标、环境、作用域、根因、变更 diff、权限、风险、成功条件、回滚条件、停止条件、观察窗口或回滚方案。新 revision 必须重新批准。

## 5. 冻结并执行单一最小变更

变更必须是针对已确认根因的单一最小 diff。冻结后记录内容摘要、哈希或可复核表示，不得在执行中顺手重构、加入 fallback、扩大网络或权限、替换无关组件，或叠加第二项试验。

执行前再次检查：

1. 当前 `packet_revision` 与批准绑定一致。
2. 真实目标状态自批准后没有关键漂移。
3. 回滚路径可执行，所需权限与产物可用。
4. success、rollback、stop conditions 可被客观观测。
5. verifier 独立于执行者，且可访问真实目标状态。

仅应用一次。若命令将产生超出冻结 diff 的效果，停止并请求新 revision。

## 6. 有界观察、失败即回滚并停止

在批准的观察窗口内只采集预先声明的指标和行为。不得因暂时未成功而即兴增加修改。

满足任一条件立即停止继续变更：

- 触发 rollback condition。
- 出现未预期影响、作用域扩张或证据冲突。
- 观察窗口到期但 success condition 未满足。
- 无法可靠观测真实状态。
- 回滚能力丢失或授权失效。

若已执行变更且 success condition 未满足，按冻结方案回滚，记录回滚证据，然后停止。回滚后不得自动尝试第二种修复。新的假设或 diff 必须创建新 revision，并重新经过诊断与授权。

## 7. 独立验收真实最终状态

最终 verifier 必须独立读取真实状态，不得采信执行 Agent 的摘要、自报测试结果或中间时点结论。

verifier 应检查：

1. 验证对象是当前真实环境、最终工作区或最终部署状态，而非旧快照。
2. 变更边界与冻结 diff 一致，无遗漏、临时文件、隐式 fallback 或额外副作用。
3. success conditions 在有界窗口内全部成立。
4. 关键负向条件未发生。
5. claim 由相匹配的 E1 至 E5 证据支持，且 `does_not_prove` 已明确。
6. 若目标包含恢复能力，已验证真实恢复与完整性，而不只是连接、传输或备份作业成功。
7. 回滚后则验证基线恢复，并将最终状态设为 `rolled_back` 或 `stopped`，不得标记 `accepted`。

只有 verifier 写入 `accepted: true` 后，事件才可完成。最终报告应给出 packet revision、实际状态、证据引用、未证明事项和剩余风险。

## 项目交付链路边界

若变更进入 PR、CI、GitOps 或仓库项目交付链路，复用现有 `production-project-iteration` 或 `codex-delegated-change` 流程。本 Skill 只负责运维证据、授权、最小变更、运行时观察和独立验收门禁，不重复实现提交、评审、PR 或 CI 编排。

## 可选薄 Adapter

仅按已观察到的失效模式启用 Adapter。它们是流程约束，不是对模型固有能力的判断。

### anti-overengineering

适用于调查范围不断扩张、输出过长或开始无证据设计 fallback 时：

- 当前轮只保留一个假设和一条下一命令。
- 禁止无证据 fallback、事故中重构和顺手优化。
- 输出限制为：假设、命令、结果、证据等级、下一状态。
- 达到预算仍无进展时标记 `inconclusive` 并停止，不用更多改动换取确定感。

### explicit-authorization

适用于批准措辞含糊、多人转述或作用域可能漂移时：

- 含糊确认不等于批准。
- 关键决策必须引用准确用户原话或批准包。
- 批准必须绑定 packet revision、冻结 diff、目标和环境。
- 无法给出准确引用时将授权视为 `not_granted`。

### search-coverage

适用于“未找到配置、日志、会话或证据”被误当作“不存在”时：

- 在下结论前声明搜索根、查询方式、命中结果和未读范围。
- 区分未找到、无权限、索引缺失、读取失败和确实不存在。
- 声明可用 fallback，例如原始日志、目标环境状态、替代控制面或第二 authoritative source。
- fallback 仍无结果时只记录 `inconclusive`，不得外推为否定事实。
